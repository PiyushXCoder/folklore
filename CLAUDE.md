# folklore — superlore Viewer

Viewer app for [superlore](https://superlore.vercel.app) docs. Opens `.superlore` bundles and plain `.mdx` files, renders them with the official `superlore` package. Ships two ways from one codebase: Tauri desktop app + plain web build.

Progress log: `progress.md`. Feature plans: `plans/`.

## Stack

- Vite + React 19 + TypeScript, Tauri 2 (`src-tauri/`) for desktop.
- Rendering: `superlore` npm package (`SuperloreDoc`, `useSuperloreMdx`, `superlore/runtime.css`). Never hand-roll MDX compilation — same renderer as the docs site and the online Viewer.

## Commands

- `pnpm dev` — web dev server (Vite, port 1420)
- `pnpm tauri dev` — desktop dev (wraps the same Vite server)
- `pnpm build` — web production build (`tsc && vite build`)
- `pnpm tauri build` — desktop bundle

## Architecture

- **`.superlore` file** (format defined by this app, not upstream): zip bundle — `doc.mdx`, `assets/` (referenced images), `comments.json` (Viewer-style comment threads), `meta.json` (title, timestamps, source path). Unzipped client-side (`src/lib/superloreFile.ts`, via `fflate`) into `{ mdx, assets, comments, meta }`. Plain `.mdx` loads as a bare source string — no comments/assets.
- **Platform split**: one `isDesktop()` check (`src/lib/platform.ts`, tests `window.__TAURI_INTERNALS__`) branches only file acquisition (`src/lib/openFile.ts`) and settings storage (`src/lib/storage.ts`). Rendering, layout, and settings UI are shared code — no per-platform component forks.
  - Web: File System Access API (`showOpenFilePicker`, drag-drop's `DataTransferItem.getAsFileSystemHandle()`) when the browser supports it (Chromium) — gives a watchable `FileSystemFileHandle`. Falls back to plain `<input type=file>` / `DataTransfer.files` (Firefox/Safari, or a handle that resolves to `null`) — works the same, just no live-reload.
  - Desktop: native open dialog (`@tauri-apps/plugin-dialog`), native drag-drop (`getCurrentWebview().onDragDropEvent`), and CLI-arg opening (`folklore path/to.superlore` / OS "Open with"). Rust side (`src-tauri/src/lib.rs`): `get_launch_path` command returns (and consumes) the launch arg captured at `run()` startup; `read_file_bytes` reads any path handed back by the dialog, drag-drop, or launch arg — both are plain `#[tauri::command]`s, not plugin commands, so they aren't gated by the capabilities ACL.
  - **OS "Open With" / double-click file association**: `tauri.conf.json`'s `bundle.fileAssociations` registers `.superlore` (`application/x-superlore`) and `.mdx` (`text/markdown`) — this drives the Linux `.desktop` MimeType, macOS `Info.plist` `CFBundleDocumentTypes`, and the Windows registry, and on all three the OS hands the opened file's path as `argv[1]`, which `get_launch_path` already reads. **Linux needs one more piece Tauri doesn't do by default**: its bundled `.desktop`-file template has `Exec={{exec}}` with no `%f`, so double-click/`xdg-open` launches with *no* file argument at all — silently defeats the whole feature. Fixed with a custom Handlebars template (`src-tauri/linux/main.desktop.hbs`, wired via `bundle.linux.deb.desktopTemplate`/`bundle.linux.rpm.desktopTemplate`) — the only change from Tauri's default (`tauri-apps/tauri`'s `crates/tauri-bundler/src/bundle/linux/freedesktop/main.desktop`) is `Exec={{exec}} %f`. Verified empirically: this same template applies to the AppImage bundle too (no separate `AppImageConfig.desktopTemplate` field exists, but it reuses deb/rpm's), so all three Linux targets pick up `%f` from one file.
- **Live-reload**: `OpenedDoc.watch` (`src/lib/openFile.ts`) carries a `WatchSource` — `{ kind: "path" }` on desktop, `{ kind: "handle" }` on web — whenever the doc came from something more than a bare `File`. `watchSource()` (`src/lib/watchSource.ts`) starts either a real filesystem watch (desktop) or a 1s `setInterval` polling `handle.getFile().lastModified` (web — no push-based watch API exists for local files in browsers). Either way it re-reads via `reloadBundle()` and replaces just the doc's `bundle`, keeping `filename`/`watch` — so `PageViewer`'s outline scan and the rest of the UI just re-render off the new content.
  - Desktop watching is a **custom `notify`-crate implementation** (`watch_path`/`unwatch_path` commands in `src-tauri/src/lib.rs`), not `@tauri-apps/plugin-fs`'s `watch()`. That plugin's `watch`/`unwatch` are ACL-scoped — this app needs to watch whatever arbitrary path the user opened, and the initial attempt (a permissive `fs:scope: ["**"]`) silently never fired (the frontend swallowed the rejected promise, too — no error surfaced). Same reasoning as `read_file_bytes`: a plain command sidesteps the fs-plugin ACL entirely instead of fighting its scope syntax.
  - **Watches the parent directory, not the file itself**, filtering events by filename. Many editors (vim, VS Code's atomic save, etc.) save by writing a temp file and `rename()`-ing it over the original — that replaces the inode, so a watch on the file's own path goes dead after the *first* save (confirmed with a standalone `notify` test: 0 events on the second atomic save). A directory watch keeps seeing the new inode every time. Fires on `is_modify() || is_create() || is_remove()` (the rename shows up as `Modify(Name(_))`) — deliberately excludes `Access` events, since our own reads (`read_file_bytes`, and the reload itself) would otherwise retrigger a reload loop. `watch_path` emits a per-call `file-changed:<id>` event; the frontend listens via `@tauri-apps/api/event`'s `listen()` and debounces 200ms (a single file write still fires multiple inotify events).
- **Window title**: `<filename> — folklore` (plain `folklore` with no doc open), set in `App.tsx` on every `doc.filename` change — both `document.title` (web tab) and, on desktop, `getCurrentWindow().setTitle()`. The desktop call needs **`core:window:allow-set-title` in `capabilities/default.json`** — it is *not* in `core:window:default`, and without it the promise just rejects into nothing. Same for `core:window:allow-close`, which File → Quit needs. Adding a `getCurrentWindow().*` call means checking whether its permission is in the default set; assume it isn't.
- **Linux decorations**: the app deliberately does **not** use GTK's client-side decorations — see Gotchas for the two-backend implementation.
- **Layout**: MS-Word-style, not a docs-site chrome. `AppShell` (`src/App.tsx`) = titlebar (filename + open button) + left `OutlineSidebar` + centered `Page` column (fixed max-width, page-like padding/shadow) wrapping `<SuperloreDoc>`. The outline is scanned off the *rendered* `h1`–`h4` DOM inside the page (`src/components/PageViewer.tsx`, via `MutationObserver`), not hand-parsed from the MDX source — that way it always matches whatever ids `rehype-slug` actually assigned.
- **Page hero**: `PageViewer` wraps `.page` (the paper card) in a `.page-container` that also holds a `.page-hero` block *above* the card — the doc's frontmatter `title`/`summary`, rendered outside the card so it reads as a document header, not page content. Deliberately outside `.page`, not inside its padding. Driven by the same `onFrontmatter` callback the metadata panel uses; local `hero` state resets to `{}` on every `doc.filename` change so the previous doc's title never flashes before the new one compiles.
- **Metadata panel** (`src/components/MetadataPanel.tsx`, titlebar "Metadata" button, only shown once a doc is open): surfaces the two metadata sources that were being parsed/computed but never actually displayed anywhere — `SuperloreDoc`'s `onFrontmatter` callback (the doc's MDX frontmatter: title, summary, tags, whatever the author put there) and, for `.superlore` bundles, `bundle.meta` (the zip's `meta.json`). Frontmatter is captured in `App.tsx` state and reset to `{}` on every new doc load (cleared before the new doc's first compile fires the callback, so it never flashes the previous doc's values). Both sections render as generic key/value lists (`Object.entries`) since neither schema is fixed — an author can put any frontmatter fields they want, and `meta.json`'s shape is whatever this app decides to write there in the future (nothing writes one yet, only `.superlore`-authoring tooling elsewhere would).
- **Copy Context** (View → Copy Context, `Ctrl/Cmd+Shift+C`): copies the selection as an editor-style source reference — `<file>:<startLine>:<startCol>-<endLine>:<endCol>` followed by the selection as a markdown quote — for pasting into Claude. The page is compiled output and carries no source information on its own, so `rehypeSourcePositions` (`src/lib/sourceMap.ts`, passed alongside `rehypeResolveAssets` in `PageViewer`'s `rehypePlugins`) stamps `data-sl-pos="line:col-line:col"` on every rendered element: `mdast-util-to-hast` copies each node's `position` onto the hast tree, and superlore appends host rehype plugins after its own, so the coordinates are there to take. A selection then resolves to its nearest stamped ancestor and the exact columns come from locating the selected text inside *that block's* slice of the MDX (repeated occurrences disambiguated by how far into the block's rendered text the selection starts). **This is deliberately not a whole-document text search** — that only runs as a last resort for selections with no stamped ancestor, and only a unique match counts.
  - Three things don't stamp, by construction: Shiki rewrites code-block subtrees (verified: 0 of 8 `<pre>`s carry the attribute — code selections resolve through the whole-source fallback instead, which works because Shiki's rendered text matches the source verbatim), MDX JSX elements like Canvas are `mdxJsxFlowElement` at the rehype stage rather than `element`, and inline markup means the rendered text isn't in the source verbatim (`**bold**`). All three fall back to the enclosing block's line range, reported as `:9-9 (approx)` with the columns dropped rather than invented.
  - The menu item is **not** gated on whether a selection exists: `useNativeMenu` rebuilds the entire native menu whenever the action list changes, so a `hasSelection` flag would rebuild it on every `selectionchange`. With nothing selected the action reports that instead.
  - `copyText` (`src/lib/docContext.ts`) tries `navigator.clipboard.writeText` and falls back to a hidden textarea + `execCommand`, restoring the user's selection ranges afterwards — the fallback steals focus and would otherwise clear the highlight at the moment you copy it.

- **Settings**: color-scheme picker (Catppuccin Latte/Frappé/Macchiato/Mocha, plus Darcula, VS Code, Adwaita) + accent swatch, via one `useSettings()` hook (`src/hooks/useSettings.ts`). Light/dark isn't a separate toggle — each scheme already implies one (Latte and Adwaita are light; the rest are dark) — `schemeMode()` (`src/theme/tokens.ts`) derives `SuperloreDoc`'s `theme` prop straight from the chosen scheme.  Storage adapter: `localStorage` always; mirrored through `@tauri-apps/plugin-store` on desktop so it persists to the app-data dir.

## Design system

- **Font**: split by area. App chrome (titlebar, sidebar, settings/metadata panels) is **Inter**, self-hosted via `@fontsource/inter` (weights 400/500/600/700, imported in `main.tsx`) — not a Google Fonts CDN link, so the desktop app doesn't need network access for its default font. The **page itself — doc content and its `.page-hero` title/summary — is the system monospace stack** (`ui-monospace, SFMono-Regular, Menlo, Monaco, Consolas, "Liberation Mono", "Courier New", monospace`), no web font needed since every platform ships one of these. Two separate override points: `.superlore-doc`'s own `--font-sans` CSS var (set directly on that element by `superlore/runtime.css`, not inherited from `body`) for doc content, and `.page-hero`'s own `font-family` for the title/summary sitting outside `.page`. (Landed here after trying Noto Sans, then Noto Sans Mono / JetBrains Mono, then Inter for both areas — system monospace for the page specifically is what stuck.)
- No raw hex in components — colors only via CSS custom properties. `src/theme/schemes.css` defines 7 color schemes (Catppuccin's 4 flavors + Darcula, VS Code, Adwaita), each providing the same var set: `base`/`mantle`/`crust`/`surface0-2`/`overlay0-2`/`subtext0-1`/`text` (app chrome) plus all 14 Catppuccin-named accent slots (`rosewater`..`lavender` — kept as the shared accent vocabulary across every scheme, even non-Catppuccin ones, so the accent grid and its CSS work identically regardless of scheme). Active scheme/accent applied via `data-scheme`/`data-accent` on `<html>` (matches superlore's own `data-theme`-on-container pattern). Darcula/VS Code/Adwaita are approximations onto that 14-slot vocabulary, not certified ports of those ecosystems' real palettes.
- **`border-radius: 2px` everywhere**, with one deliberate exception: `.kp-canvas-node` (superlore Canvas's shape-surface class — `SURFACE` const in `node_modules/superlore/dist/components/canvas/nodes.mjs`) is excluded via `*:not(.kp-canvas-node)` in the global rule. A Canvas node's radius is semantic geometry (circle, diamond, pill), not decorative rounding — forcing 2px there turned circles into squares and pills into rectangles. (First attempted fix, `.react-flow * { border-radius: revert !important }`, didn't work: `revert` rolls back to the *user-agent* default — `0` — not to whatever lower-specificity author rule set the real radius, so it looked identical to the bug. `:not(.kp-canvas-node)` on the source rule is the actual fix — verified with circle/diamond/rounded node kinds before and after.) One global rule in `schemes.css`, applied after `superlore/runtime.css` import so it wins the cascade everywhere else.
- `SuperloreDoc` is re-skinned via its `tokens` prop (`src/theme/tokens.ts`'s `SUPERLORE_TOKENS`) — every value is a `var(--app-*)` reference, never a resolved color, so a scheme/accent change re-colors the doc for free with zero re-render logic (no branching on theme in JS).

## Logo / icon

- `src/assets/accordion.svg` (also copied to `public/accordion.svg` for the web favicon) is the one source icon, used everywhere: web favicon (`index.html`), titlebar + empty-state logo in the UI, and every Tauri app icon (`src-tauri/icons/`, generated via `npx tauri icon src/assets/accordion.svg` — desktop/iOS/Android/Windows-Store sizes, `.icns`, `.ico`). Regenerate the Tauri icon set with that same command if the source SVG ever changes; don't hand-edit the generated files in `icons/`.

## Release / CI

- **`.github/workflows/release.yml`** — triggers on pushing a `v*.*.*` tag or manual `workflow_dispatch`. `build-tauri` matrixes Ubuntu/Windows/macOS (both `aarch64`/`x86_64` targets) via `tauri-apps/tauri-action`, uploaded to a **draft** GitHub Release (`releaseDraft: true` — review and publish manually). `NO_STRIP: true` is set for all platforms (harmless on Windows/macOS, required on Linux — see Gotchas). On a manual dispatch off a branch (no tag), `tagName` falls back to `github.ref_name` (the branch name) — re-running dispatch on the same branch updates that same draft release rather than erroring on a duplicate tag.
- **`.github/workflows/pages.yml`** — separate workflow, deliberately: triggers on push to `master` or manual dispatch, builds the plain web app (`pnpm build`) and deploys `dist/` to GitHub Pages. Kept **out** of `release.yml` because the `github-pages` environment's deployment branch/tag policy (auto-created when Pages is first enabled) defaults to allowing only the repo's default branch — a tag-triggered deploy gets rejected with "Tag `vX.Y.Z` is not allowed to deploy due to environment protection rules," since a tag ref doesn't satisfy a branch policy. One-time repo setup needed: Settings → Pages → Source → "GitHub Actions".
- **AUR package**: `packaging/aur-bin/PKGBUILD` (+ `.SRCINFO`) — a `-bin` package, `aur.archlinux.org/folklore-bin.git`. Not built from source: it downloads the GitHub Release's `folklore_<ver>_amd64.deb` and just re-lays out its `usr/` tree (`ar x` the `.deb`, extract `data.tar.gz` straight into `$pkgdir`) — same binary the `.deb`/AppImage ship, only repackaged for pacman. Bumping the version means: update `pkgver`/`sha256sums` in `PKGBUILD` (checksum from the new release's `.deb` asset), regenerate `.SRCINFO` (`makepkg --printsrcinfo > .SRCINFO`), commit+push to the AUR git remote (separate from this repo's remote — `ssh://aur@aur.archlinux.org/folklore-bin.git`). `makepkg` build artifacts (`pkg/`, `src/`, downloaded `.deb`, `.pkg.tar.*`) are gitignored; only `PKGBUILD`/`.SRCINFO` are tracked here as the source of truth, mirrored to the AUR repo.

## Gotchas

- **`NO_STRIP=1` is required for Linux AppImage bundling** (`pnpm tauri build`, or CI). `linuxdeploy`'s bundled `strip` is an older `binutils` build that can't parse the `.relr.dyn` ELF section (`DT_RELR`-packed relocations) modern system libraries emit — it fails on every `.so` it tries to strip, and the whole bundle step dies with `failed to run linuxdeploy`. `NO_STRIP=1` skips linuxdeploy's strip pass entirely; the release binary is already stripped by `cargo build --release` regardless, so nothing is actually lost.

- **WebKitGTK latches a scrollbar drag when the compositor steals the pointer grab** (`src/hooks/useScrollLatchRecovery.ts`). The scrollers sit flush against the window edges, which is where the compositor's resize border is — resize the window mid-drag and the webview gets the button press but never the release, so the scrollbar stays latched and the doc scrolls on bare mouse movement until the next click. Clearing it means *destroying* the scrollbar: flipping `overflow` for one layout pass works; `::-webkit-scrollbar { display: none }` does not (the latched scrollbar object survives it); and flipping while the compositor still holds the button lets the latch re-form, hence the staggered retries.
  - **The page cannot detect this state, and trying to is a trap that was already sprung once.** While a native scrollbar drag is in progress the engine dispatches no mouse or pointer events whatsoever (verified in a real WebKitGTK window: zero `mousemove`/`pointermove`/`mouseup`, only `scroll`) — and that is equally true of a *legitimate* drag. A "ghost scroll" heuristic (scroll events with no input behind them) therefore cannot tell a latched scrollbar from a user who is simply still dragging, and shipping one tore the scrollbar down mid-drag after ~800ms, leaving the thumb stranded. **Don't reintroduce it.** The trigger has to be a window resize, which essentially can't co-occur with a legitimate drag — the webview holds the implicit grab for the whole drag, so a resize starting mid-drag means the grab was taken away.
  - Known gap: a grab stolen for something that *isn't* a resize (a compositor window-move, say) leaves the latch in place until the next click, since no resize event ever fires. Closing that needs the GTK side — `grab-broken-event` on the window, then polling the pointer's button mask until it's released before telling the frontend to flip — which fires exactly on a steal and never during a real drag.
  - **Reproducing any of this needs a real window and a stolen grab** — a scripted drag in Chromium/Playwright, or in WebKitGTK without the steal, always releases cleanly and shows nothing. The harness that does catch it: Xvfb + `xdotool` driving the built app in a `WebKit2.WebView`, with a second GTK surface taking a `Gdk.Seat.grab()` mid-drag to mimic the compositor. Any change here must also be checked against a **slow, multi-second drag** — the regression above sailed through a short one.

- **No GTK client-side decorations on Linux** (`prefer_server_side_decorations` / `undecorate_on_wayland` in `src-tauri/src/lib.rs`). GTK3 draws its own titlebar with its own min/max/close buttons: themed by GTK rather than the desktop, duplicating the title the WM already shows, and — since `set_title` updates the Wayland toplevel but *not* GTK's headerbar label — showing a **stale** title while the compositor shows the right one. The fix is backend-split, and the split is the whole point:
  - **X11** — `GTK_CSD=0` (GTK's documented opt-out), set as a default at the top of `run()`, before GTK initializes. The WM decorates the window instead.
  - **Wayland** — `GTK_CSD` is silently ignored. `gtk_window_should_use_csd()` returns TRUE unconditionally for a Wayland display *before* it reads the variable, because GTK3 never implemented the `xdg-decoration` protocol and therefore has no server-side path at all. **Verified, not inferred**: with `GTK_CSD=0` set, a niri window screenshot still showed the full GTK titlebar. So there is no SSD to fall back to and the only non-CSD state is *undecorated* — `set_decorations(false)` in `setup()` whenever the Wayland backend is detected. `GDK_BACKEND` is checked before `WAYLAND_DISPLAY`, since `GDK_BACKEND=x11` on a Wayland session goes through XWayland where the `GTK_CSD=0` path does work.
  - Applied to **every** window via a `tauri://window-created` listener, not just `main` — the About window is a second real toplevel and would otherwise be the only thing left wearing a GTK titlebar.
  - Accepted trade-off: on a *floating* Wayland compositor there's no titlebar left to drag or close with the mouse (File → Quit, About's own Close button, and the compositor's Super+drag cover it). Tiling compositors, which is where this came from, frame and label the window themselves.
  - **Verifying decoration changes needs a real window, and `pnpm dev` in a browser can't show any of this.** On niri, `niri msg -j windows` gives the toplevel title (the compositor's view, independent of GTK's headerbar) and `niri msg action screenshot-window` captures just the app window — enough to check both the title and whether a GTK titlebar is being drawn, without screenshotting the whole desktop.

- **`vendor/next-shim`**: superlore's `Canvas` component (`superlore-canvas` fenced blocks) imports `next/dynamic.js` directly and unconditionally — even though `next` is an *optional* peer dep and this app has no Next.js. Vite's optional-peer-dep handling throws at runtime the moment that import is reached (a real white-screen cause, not a build-time error), and a plain `resolve.alias` doesn't intercept it — Vite's dep-optimizer special-cases "known-optional-and-not-installed" before alias resolution runs. Fix: `vendor/next-shim` is a real (tiny, local) `next` package — `"next": "file:./vendor/next-shim"` in `package.json` — whose `dynamic.js`/`dynamic` exports are a `React.lazy` + `Suspense` equivalent. Because it's a genuinely resolvable package, Vite treats it as normal and never engages the optional-peer-dep path. Don't remove this dependency without re-testing Canvas rendering.
- **Canvas edges/arrows invisible in the desktop app only** (`src/app.css`, the `.react-flow .react-flow__edges` rule): superlore's compiled CSS is missing `@xyflow/react`'s own base rule for its per-edge `<svg>` wrappers (`node_modules/@xyflow/react/dist/style.css`'s `.react-flow .react-flow__edges svg { overflow: visible; ... }`) — each edge renders in its own un-sized `<svg>`, relying on `overflow: visible` to paint past its default 300×150 intrinsic box. Chromium (so: headless Playwright testing, and `pnpm dev` in a browser) happens to paint past that box anyway; WebKitGTK (Tauri's real engine) still force-clips the *outermost* `<svg>` to its own box regardless of the `overflow` property (confirmed empirically in a real `tauri dev` window: computed style showed `overflow: visible`, but a path point past the box edge still didn't paint — an old SVG1.1-era "root svg always clips" behavior some engines never dropped). **This means Chromium/Playwright testing cannot catch Canvas rendering bugs — verify in an actual Tauri window (or at minimum Safari/WebKit) before calling Canvas changes done.** Fix: give the edges `<svg>` real fixed pixel dimensions (`width/height: 8000px`, flow-space coordinates, not a CSS percentage) so there's no nearby box edge to clip at — doesn't cover diagrams whose layout goes negative from `(0,0)`, but superlore's elkjs-based auto-layout keeps everything positive in practice.
